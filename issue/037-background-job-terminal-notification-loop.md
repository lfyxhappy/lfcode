# 后台任务完成通知自唤醒模型，导致会话重复检查并形成循环

## 问题

生产使用版会话 `ses_067fa1b3bffe3XHakfhoQxIgBa` 在创建图片压缩 skill、随后以 8 个 worker 压缩图片时，出现了持续重复“查看后台进程 + 日志”、`task.list`、`memory.search` 和状态叙述的现象。用户看到的是相近的对话不断重放，容易误以为上下文丢失或前端重复渲染。

本次业务任务本身是有效且最终成功的：图片压缩 skill 已创建并被调用；最终一次压缩在 `2026-07-25 16:10:08` 完成，统计为总计 2766 张、压缩 1242 张、跳过 1524 张、错误 0、仍大于 5MB 的 15 张，耗时约 1.1 分钟、约 42.3 张/秒、`workers=8`，stderr 为空。最终 assistant 消息在 `16:10:35` 以 `finish: stop` 结束。因此本 issue 不把“创建 skill”或“图片压缩失败”当作原因，也不把最后的成功结果表述为已经证明整机 CPU 被完全打满。

会话记录显示该循环具有明显的运行时反馈特征：

- 共有 168 个已完成后台 job、4 个失败 job，其中 83 个标题为“查看后台进程 + 日志”。
- 共有 137 次 `shell_process`、93 次 `task`、43 次 `memory` 调用。
- `task` 始终为空：本任务没有被持久化为 task；`actor` 也始终为空：压缩通过 PowerShell `Start-Process` 启动，而非 actor 工具。
- `memory.search` 不能提供当前运行态，反复查询只返回无关或无新增价值的历史记录。
- “按系统提示核对会话状态”等重复表述是模型在缺乏终态结果时的重复决策，不是前端把同一条消息渲染了多次，也没有找到固定源码提示词会强制输出该句。
- 早期还存在短周期轮询放大：模型反复执行“查 Python 进程 + 读日志”，每次只得到少量新增信息，却没有采用有间隔的等待、累计进度汇报或无进展停止条件。

## 原因

### 已确认的事件链

1. `shell_process` 创建持久化后台 job。
2. job 结束时，`packages/lfcode/src/background-job/runtime.ts:436` 发送 `actor_notification`。终态内容只有“Shell process completed”、`job_id` 与 `title` 等状态元数据，未携带 stdout、stderr、退出码或结果摘要。
3. `packages/lfcode/src/inbox/render.ts:4` 将该类 inbox 项按预渲染通知正文交给会话；会话执行把它视作新的可处理输入，唤醒下一轮模型。
4. 新一轮模型只知道某个 shell job 已完成，却不知道任务结果，于是再次执行状态检查、读日志或启动新的 shell 检查 job。
5. 新 job 完成后又产生同类通知，形成“完成通知 → 新模型轮次 → 新检查 job → 完成通知”的自触发回路。

本会话还叠加了进程归属断裂：压缩由 PowerShell `Start-Process` 启动，启动器 shell 可以先正常退出，而实际 Python 压缩进程仍在运行。此时 shell job 的“completed”只说明启动命令结束，并不等价于压缩任务完成；若运行时没有跟踪或等待被分离的子进程，就会过早触发通知，迫使模型再用轮询猜测真实进度。

### 上下文并非完全缺失，但当前机制放大了循环

- 已完成工具调用的旧输出在活跃上下文中会被替换为占位内容，见 `packages/lfcode/src/session/message-v2.ts:1203`。这是控制上下文体积的既有策略，并不等价于会话历史被删除。
- 更直接的缺口是终态通知没有携带结果。即使模型保有对话目标，也无法从通知本身判断压缩是否完成、失败或需要继续处理。
- `packages/lfcode/src/tool/background_job.ts:182` 的 `shell_process.wait` 是模型主动获取后台 job 结果的正确边界；但普通 job 完成通知仍会无条件触发模型，混淆了“界面状态更新”和“需要模型继续推理”两件事。
- 模型把每次唤醒当成必须做 `task`、`actor`、`memory` 预检的动作，是循环的次级放大器；这些工具在该会话均无法产出推进信息。
- 用户已经发送停止、转向或新的任务指令时，早先 job 的迟到终态通知仍可能进入当前 activity；缺少 activity/代际隔离会让已经失效的监控链重新唤醒模型。

## 推荐解决方案

不要把每一段完整工具日志直接塞回上下文。完整日志可能很大、含噪声或敏感数据，且会进一步挤占模型的有效工作上下文。应把“可推进决策的有界结果”与“完整可追溯日志”分层处理。

1. **让显式等待获得有界终态结果。** 扩展 `shell_process.wait` 的终态返回，至少包含 `job_id`、终态状态、退出码、stdout 尾部、stderr 尾部与截断标记；建议 stdout 保留 4–8KB、stderr 保留约 4KB。完整输出继续存放在 `background_job_log`，按需读取。
2. **普通后台完成只更新状态，不自动唤醒模型。** detached/background job 的完成、失败、取消应持久化并推送 UI，但除非模型正在显式 `wait` 该 job，或用户发送了新消息，否则不得创建新的模型轮次。
3. **若确实需要异步投递，使用专用结果事件。** 事件应明确标识为后台 job result，而不是合成用户消息；包含上面的有界结果摘要，并按 `job_id` 维护已消费/已确认状态，避免同一 job 多次继续模型执行。
4. **保留有限的近期结果摘要。** 在 active context 的历史裁剪后，保留最近若干后台 job 的结构化摘要（job、状态、退出码、stdout/stderr tail、是否截断），不保留整份日志。这样在用户追问或模型下一步决策时仍有足够事实。
5. **加入运行时防护。** 对同一 session 检测“终态事件唤醒后又只创建监控 job”的重复模式；同一 job 最多触发一次被确认的继续，连续无新信息的监控循环应合并、抑制或要求用户/模型显式等待。
6. **把模型引导作为第二道防线。** 更新工具说明或系统策略：收到完成事件时先读取该 job 的一次结果并作出“汇报、继续、停止”之一；不得因为通知到达而强制执行 `task`、`actor`、`memory` 三连预检；无新信息时应停止轮询。
7. **保持真实子进程与 job 的归属一致。** 长任务应直接由受管 shell job 执行，或以 `Start-Process -Wait -PassThru` / 等价机制把实际进程退出码和输出纳入该 job；若确需 detach，必须显式登记子进程 PID、生命周期和结果采集方式，不能把启动器结束伪装成业务完成。
8. **为通知增加 activity fence。** 终态事件携带创建它的 activity/代际标识；用户停止、steer 或开始新 activity 后，旧 activity 的通知仅供 UI 查看，不得重新驱动当前模型。

### 建议实施顺序

1. 先拆分后台 job 的 UI 通知与模型输入路径，关闭普通终态事件的自动模型唤醒。
2. 为 `shell_process.wait` 补齐结构化、有界终态结果和日志截断语义。
3. 如产品仍需要后台完成后自动继续，增加专用结果事件、确认状态及按 `job_id` 去重。
4. 为分离式子进程增加受管等待或显式 PID 追踪，避免启动器完成被误判为业务完成。
5. 最后加入会话级循环检测、activity fence 和模型提示，作为协议缺陷之外的兜底。

### 验收标准

- 对一个被显式等待的 job，`shell_process.wait` 在同一工具交互内返回退出码及 stdout/stderr 摘要；超过上限时明确返回截断标记，完整日志仍可访问。
- detached job 完成时，UI 可以显示终态，但不会在没有显式 wait 或新用户输入的情况下调用模型。
- 大量 job 同时完成时，每个 `job_id` 最多造成一次已确认的 continuation；重复投递、重连和重放不会制造新的监控 job。
- 通过 `Start-Process` 启动的长任务不能在启动 shell 退出时被标记为业务完成；验证受管等待或显式 PID 跟踪能给出实际进程的终态、退出码与结果。
- 用户已经停止或转向后，旧 activity 的迟到 job 通知只更新 UI，不得唤醒当前 activity 的模型。
- 历史工具输出被裁剪后，最近后台 job 的有界结果摘要仍可用于判断任务终态，而不是只剩“Shell process completed”。
- 对本会话类型复测时，模型不会在无新信息条件下反复调用 `task`、`actor`、`memory` 或创建“查看后台进程 + 日志”job。
- 先完成 `packages/lfcode` 的定向单元/集成测试；桌面验证只在 `C:\算法\小应用\Lfcodepre` 进行，不停止、覆盖或同步生产使用版 `C:\算法\小应用\Lfcode`。
