# 补丁上下文失配后的模型重复猜测和绕过编辑工具

## 优先级

高

## 状态

已解决

## 当前实现

- context mismatch 后目标文件进入恢复状态：必须通过 `read` 取得新版本；文件随后变化会使该读取失效。
- 同一编辑回合对同一目标第二次 mismatch 会熔断，`apply_patch`、`edit`、`write` 和已识别的 shell/Python 写入都会拒绝绕过。
- 成功结构化编辑会清除恢复锁。仍待使用版真实长会话复现一次失败后续跑链路。

## 问题

在长会话和连续文件编辑过程中，模型可能根据记忆生成不存在的补丁上下文。`apply_patch` 正确拒绝后，模型又继续猜测标题、重复提交补丁，甚至改用 shell/Python 直接写文件，最后仍可能把“工具调用完成”误判成“任务完成”。

这会造成无效重试、文档段落被意外吞掉、编辑规则被绕过和错误的完成声明。问题已在会话 `ses_0b3b035d0ffe692Q2i1HqTM7yD` 中复现。

## 原因

1. 模型提交了文件中不存在的上下文。例如把实际的“`重蹈覆辙`”写成“`重蹈覆覆`”，以及引用当时不存在的“`自动拍平硬条件(...)`”标题。
2. `apply_patch` 失败后没有强制模型重新读取目标文件。模型可以继续使用旧上下文或刚刚计划写入的内容作为旧文本。
3. 当前失败信息只说明“找不到上下文”，没有返回文件行号、最接近的真实文本或建议的精确编辑范围，恢复成本较高。
4. 成功补丁只证明文本变更已应用，不证明模型想保留的语义段落仍然存在；本次会话中模型自己报告一个成功补丁吞掉了旧的“拍平硬条件”段。
5. 长会话包含大量历史消息和工具输出，模型的文件状态记忆容易与真实文件脱节。此次会话共有 164 条消息、628 个 parts，使用 MiniMax-M3；这是风险放大的因素，但不是工具误判的证据。

已确认 `apply_patch` 会读取当前文件、先完成上下文验证，再执行写入；因此本次“找不到上下文”的拒绝本身符合设计，不应通过简单放宽匹配来规避。

## 推荐解决方案

1. 增加统一的补丁失败恢复协议：
   - 第一次验证失败后，运行时向模型注入结构化指令：必须重新读取目标文件，不得猜测上下文。
   - 下一次编辑前必须出现针对同一文件的 `read`，并只能使用读取结果中的原文。
   - 小范围修改优先改用 `replace_range`；只有明确需要多段或多文件变更时才继续使用 `apply_patch`。
   - 同一文件连续失败两次后熔断当前编辑链，要求模型重新整理目标，不得继续重试。

2. 强化工具错误信息：
   - 返回目标文件中的行号和附近真实文本。
   - 返回最接近的候选上下文，但候选只能用于提示，不能自动模糊应用。
   - 区分“上下文不存在”“旧内容不匹配”“文件已被外部修改”和“补丁格式错误”。

3. 增加读取版本保护：`read` 返回文件版本或 hash，编辑工具携带 `expectedHash`。文件在读取后发生变化时，明确报告“读取已过期”，而不是让模型继续使用旧文本。

4. 限制失败后的绕过写入：在一次编辑恢复链中，`apply_patch` 验证失败后禁止使用 shell/Python 对同一目标文件写入；shell/Python 只能执行实际运行或测试命令。

5. 增加成功后的语义复核：
   - 编辑工具成功后自动重新读取变更范围并返回最终内容摘要。
   - 对 Markdown skill 文件增加 frontmatter、重复标题和关键段落检查。
   - 模型只有在复核成功后才能声明完成。

6. 控制长会话风险：大型任务完成后，把 skill、配置和文档收尾拆成独立轮次；对超长工具输出做摘要或截断，避免模型继续依赖过期的完整上下文。

7. 增加测试：覆盖上下文错字、文件外部变化、连续失败熔断、失败后禁止绕过写入，以及成功补丁删除关键段落后的语义检查。
