# 测试提示词目录规则

## 目录用途

- 本目录统一存放用于评估模型能力的测试提示词，不存放被测项目源码、运行产物或截图。
- 每个测试提示词使用一个独立的 Markdown 文件，正文必须可以直接复制给被评估模型。

## 文件命名

- 文件名使用小写英文或短横线分隔，例如 `threejs-racing-evaluation.md`。
- 文件名应描述测试主题，不使用 `final`、`new`、`最新` 等容易失真的版本词。
- 同一测试的修订应直接更新原文件；只有评测目标或约束发生实质变化时才新建文件。

## 提示词结构

每个文件至少包含以下部分：

1. `目标`：说明要评估的能力和任务结果。
2. `技术约束`：运行环境、依赖、素材、时间和禁止事项。
3. `必须实现`：可观察、可验收的核心功能。
4. `工程要求`：代码组织、错误处理、兼容性和性能要求。
5. `交付与自测`：交付文件、运行方式、已知限制和真实验证结果。
6. `评分标准`：优先使用可量化的分项评分，避免只描述主观印象。

## 编写规则

- 明确区分硬性要求、优先级和可选加分项；不要把加分项写成隐含硬要求。
- 时间受限任务必须要求模型先完成核心闭环，再补充视觉或高级功能。
- 优先使用程序化素材和可复现依赖，避免评测结果被本地资源或环境差异主导。
- 要求模型诚实报告未实现内容和自测范围，不接受虚构的测试结果。
- 约束应服务于能力评估；不要加入与评测目标无关的复杂部署、账号或外部服务要求。
- 修改提示词后检查：任务是否仍能在目标时限内完成、验收项是否可观察、评分项是否互相重叠。

## 新增提示词验收

- 文件可独立阅读和复制，不依赖本目录之外的说明才能理解任务。
- 至少包含一个明确的运行结果和一个明确的失败/未完成报告要求。
- 如涉及前端或游戏，必须写明运行入口、浏览器/视口验收和控制台错误检查要求。
- 如涉及外部模型或服务，必须写明不可用时的降级行为，不把网络可用性当作唯一能力指标。
